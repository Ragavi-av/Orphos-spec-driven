# Sub-skill: architecture-ui

You are the handler for UI route units. You receive:
- `repo_root`: the git repo root (all unit paths are relative to this)
- `confirmed_root`: the user-approved folder (never read outside it; may be a subfolder of the repo)
- `layer`: the layer tag assigned by the orchestrator (e.g. `experience`, `mobile`)
- `units`: list of repo-relative unit paths, one per line
- `output_file`: repo-relative path where you must write the result (e.g. `docs/architecture/ui/experience.md`)
- `commit`, `run_timestamp`: for the metadata header
- `exclusions`: folders the orchestrator marked as excluded (for your reference; do not read them)

## Process

1. **Read shared references** first (all from `.claude/skills/architecture-understanding/references/`):
   - [guardrails.md](../architecture-understanding/references/guardrails.md) — §A mandatory, §B what to capture
   - [doc-template.md](../architecture-understanding/references/doc-template.md) — section order and content
   - [layer-map.md](../architecture-understanding/references/layer-map.md) — context only (you work from the routed units)

2. **Read each unit** specified in `units`:
   - `package.json` (all deps/devDeps, script names, entry point, name/version)
   - TypeScript/JavaScript source in `src/`, `components/`, `lib/` (grep for export defaults, hooks, major components)
   - HTML entry point (`index.html`, `main.html`, layout file)
   - Build config (`vite.config.*`, `webpack.config.*`, `tsconfig.json`, `next.config.*`, `nuxt.config.*`)
   - `README.md` or `.md` for context, but **never** cite it as evidence
   - Android: `AndroidManifest.xml`, `res/layout/*`, gradle `build.gradle(.kts)`, `MainActivity.java`
   - iOS: `Info.plist`, SwiftUI/UIKit source stubs

3. **For each unit, extract** (do not document guesses or defaults):
   - Component names and responsibility (grep `export function/const … = …`, `class … extends …`)
   - UI framework and major dependencies (React, Angular, Vue, Solid, etc.)
   - Does it use `@module-federation/*`? If so, list the remotes/host it consumes/exposes.
   - Inbound APIs: HTTP endpoints it calls (grep `fetch`, `axios`, `WebClient`, `HttpClient`, URLs in env/config)
   - Outbound: REST endpoints, WebSocket connections, auth flow (local storage, cookies, OIDC/OAuth provider)
   - State management (Redux, Zustand, Pinia, MobX, props, Context; grep package.json + imports)
   - Routing (React Router, Vue Router, Angular routing; grep `useNavigate`, `useParams`, `routerConfig`)
   - Forms & validation (React Hook Form, Formik, VeeValidate; grep imports)
   - Build & deployment: target environments, env-var usage (`process.env`, `.env`, build scripts)
   - Android: Activities, Fragments, Services, Navigation graph; BFF endpoints (grep HttpClient base URLs)
   - iOS: ViewModels, NavigationStack; API endpoints (grep URLSession/Alamofire)
   - Accessibility: ARIA labels, semantic HTML, a11y package usage

4. **Walk dependencies up to depth 2** (your unit → direct deps; direct deps → their deps):
   - Does it consume any MCP servers, agents, or domain services (grep for hostnames / env vars in code)?
   - Does it expose APIs to other frontend units (micro-frontend exports)?
   - Any Kafka producers/consumers (unusual but flag if found)?

5. **Components diagram** (Mermaid `flowchart TB`):
   - Your UI units as boxes
   - Neighbouring layers (BFF, MCP, domain services) as styled boxes (dashed borders)
   - Data flows (HTTP, WebSocket, module-federation remotes)
   - Keep under 25 nodes; split if needed

6. **Key flows** — pick the workflows that matter:
   - User login → shell (if this unit is the shell)
   - A typical data load (e.g. user navigates to a feature → API call → display)
   - Real-time update (WebSocket, SSE, or polling)
   - Each flow: one `sequenceDiagram`, then numbered steps citing the file/line or class

7. **Write to `output_file`** using the [doc-template.md](../architecture-understanding/references/doc-template.md)
   sections (1–10). Omit sections that truly do not apply (no Kafka → skip that row, with a one-line note).
   **Metadata header:**
   ```markdown
   # <Layer name> (UI)

   > Generated by the architecture-ui skill from commit `<commit>` on <date>.
   > Evidence paths are repo-relative. Tags: [inferred] [not implemented] [unverified].
   ```

8. **Guardrails in this layer** (doc §9):
   - Security: are login/auth flows enforced? CSP headers, XSS prevention?
   - Multi-tenancy: is the tenant injected into API calls (header/URL/state)?
   - State safety: can stale data/auth leak between tenants?
   - Module-federation: are remote URLs validated? Can a malicious remote be injected?
   - Form validation & XSS: user input sanitized before display/API?
   - Accessibility: semantic structure, keyboard nav, a11y tree?
   - Link to [guardrails.md](../architecture-understanding/references/guardrails.md) if your findings map to existing rules; add new rows as needed.

9. **Gaps & drift** (doc §10):
   - Typos/stale paths in comments?
   - Mock data still in production code?
   - Unfinished flows (`// TODO`, stubs)?
   - CSP/CORS issues, missing headers, open endpoints?
   - Performance concerns (unbounded lists, missed memoization)?
   - Each item: path + observation, no code changes.

10. **Verify before finishing:**
    - Every cited path exists and you read it (not inferred from name)
    - Every component/hook name matches an actual export in the source
    - Every endpoint URL appears in code (grep the full URL or env var name)
    - Mermaid diagrams parse (no unquoted `()`, `/`, `,` in labels; quote them)
    - All sections have content or a one-line omit reason
    - No secrets, no PII (values of `.env` keys are out; env *var names* are fine)

## Output format

When done, append a **ROUTE-RESULT block** in this exact format:

```
ROUTE-RESULT
units_routed: <comma-separated unit names from input, or "none">
units_skipped: <unit>:<reason>, … (or "none")
output_file: <path you wrote to>
status: success | partial | failed
details: <one line summary; if failed, the error>
reclassify: <unit>:<new_route>:<new_layer>:<reason> (one per line; or "none")
```

Examples:
```
ROUTE-RESULT
units_routed: frontend/shell, frontend/remotes/ai-copilot, frontend/packages/eip-shell-context
units_skipped: none
output_file: docs/architecture/ui/experience.md
status: success
details: 3 components documented, flows traced to web-bff-service
reclassify: none
```

```
ROUTE-RESULT
units_routed: mobile/android
units_skipped: none
output_file: docs/architecture/ui/mobile.md
status: partial
details: main flows documented; Firebase auth integration not implemented [not implemented], skipped
reclassify: none
```

## Error cases

- Output file cannot be created → write the error message and exit
- A unit path does not exist → skip it, record in `units_skipped`
- Unit is a directory but has no source code (empty, gitignored content only) → skip, reason "no source"
- Sub-directory of a unit contains another manifest (e.g. nested module) → it should not have been routed to you; record a reclassification proposal (e.g. `frontend/remotes/widgets → service` if it has a Dockerfile)

## In this repo

- `frontend/shell` is the host; `frontend/remotes/{ai-copilot,decision-log,…}` are consumed remotes — document both the host and each remote's contract (entry point, props)
- `mobile/android` — document the main Activity, BFF endpoints, and the flow to the mobile-proxy
- Navigation in shell is React Router v7; remotes may have their own routing
- Auth: Keycloak OIDC via the shell; remotes inherit the session
- API base URL is set at build time (VITE_BACKEND_URL, NEXT_PUBLIC_API_BASE); document the *variable name*, never hardcoded IPs
- ArcadeDB/Ollama may be on an external host; widgets query them via the BFF (graph-proxy, nl-query endpoints)
